# Maintenance jobs

Inspect `~/.geppetto/machine.json`, live jobs and the memory repository's root `jobs.md` first. Pull its remote before proposing attachment. Reuse any machine's registration for `curate-skills` or `maintain-memory`, reporting “already scheduled on <machine>”; `--add-job <name>` requests another on this machine. Prefer the harness's native recurring tasks/automations. New jobs run weekly, Monday at 09:00 local time, using the [curation](../../geppetto-adopt/assets/templates/jobs/curate-skills.md) and [memory](../../geppetto-adopt/assets/templates/jobs/maintain-memory.md) prompts. Signal learning uses Stop.

Installation records ownership in `jobs.md` as `Machine | Job | Scheduler | Cadence | Registered` before activating jobs. `pending` identifies an installation still attaching its scheduler; another machine reports it as pending instead of creating a duplicate. Registry-only commits use `Memory-Event: save`; competing writers reread ownership before activation. Unrelated local commits require separate synchronization before publication. Without bucket memory, the machine registry owns job reuse.

Last-project uninstall stops owned OS jobs before removing this machine's rows. For a native or external scheduler, disable its jobs through that scheduler and pass the same registrations with `status: "disabled"` in `--scheduler-jobs`; until confirmed, the shared rows remain. Failed cleanup retains the project and installation manifest for retry. Maintenance runners execute only jobs marked `scheduled`.

Pass native registrations in an external JSON file to installation's `--scheduler-jobs`: each job name maps to `scheduler`, `id`, `cadence`, `nextRun` and `disable` strings. Otherwise installation uses Windows Task Scheduler (hidden launcher) or weekly cron with the subscription CLI; other cron cadences require native registration. Machine registration retains shared identities. Only an absent scheduler produces `needs-scheduler`; registration errors remain blockers. OS run output is retained in `~/.geppetto/<job>.log`. Report cadence, next run and controls in the recap.

OS jobs invoke the shared maintenance launcher recorded on the machine. Each installation refreshes that entrypoint and the registered prompt sources to the selected package. Windows retains the hidden `maintenance.vbs` launcher and task names; cron reconciles its marked entries in place while preserving their cadence and unrelated jobs. Native scheduler registrations retain their identities.

`curate-skills` saves a dated report for each audited project under the shared Git runtime directory `geppetto/weekly-metrics/`. It summarizes two weeks of operation timings, storage, merged pull requests and recorded Geppetto overhead. The curator can add up to two proposed experiments and their decision rules through its file tools.

Exercise new jobs on synthetic inputs before enabling them. Skill curation uses the [bounded learning CLI](ingestion.md). Memory maintenance uses the JSON exchange described below. Read [process execution](../../geppetto-adopt/references/processes.md) before launching tools.

## Observability

The machine registry records job identity, cadence, next run, package-relative prompt source and disable command; `jobs.md` exposes cross-machine ownership. The stable launcher resolves the newest complete stable version in its plugin cache at runtime; source-checkout installations use their recorded checkout. Prompts come from the executing package. `node ~/.geppetto/bin/maintenance-launcher.mjs --run <curate-skills|maintain-memory> --dry-run` reports the resolved source, host and destinations without executing maintenance. Git synchronization failures are installation errors. SessionStart links to the last successful report when it is more than eight days old. `audit.mjs --metrics` counts observed report reads. Missing measurements remain unknown and failed curation keeps the previous report.

For skill curation, the launcher appends a timestamped outcome to the per-job log, including for dry runs. Failures include a redacted diagnostic, and missing project paths are logged and skipped. Subscription output appends to the same log; the hidden Windows launcher propagates the child exit status. Tests use two clones sharing a local bare remote to verify deduplication, explicit attachment and row removal. Upgrade tests delete the old plugin cache and run both jobs without re-registration. Synthetic schedulers preserve host jobs; live attachment is an installation check.

Memory maintenance reads Git revisions from the configured checkout. The first run or rewritten history uses a snapshot. Later runs consider changes per bucket, deterministic checks for duplicate index rows, broken links, unindexed pages and missing or stale provenance, and a slow rotation of old pages. Staged, dirty and hidden Git entries are skipped. Files under `buckets/*/claude/` serve as read-only comparison evidence. The default scope covers shared buckets. Personal pages in `buckets/private` require explicit selection.

A clean scan records `no_change` with zero model calls and zero tokens. Unambiguous mechanical repairs go straight to verification. Other candidates go to a proposer in one JSON batch of up to six items from the same collection. Each rewrite accounts for the original claims and states when behavior would change. After deterministic validation, a separate reviewer sees the old text, new text, claims, behavior change and cited evidence. Each call starts Codex CLI in a fresh temporary workspace and profile containing only minimal configuration and file-based subscription authentication. The runner exchanges JSON on standard input and output. Its tool configuration disables shell, file editing and plugins. Install and sign in to Codex CLI on the machine that runs this job, regardless of which application schedules it.

The script keeps rejected and unresolved text in place, applies accepted changes in a temporary Git worktree and checks the staged paths and contents. It integrates a single local commit by fast-forward with Git hooks disabled. A moved branch or conflicting local edit yields a retriable result. Reverting that commit reverses the run.

Match the run ID in `~/.geppetto/health.json` to its scan, runner calls, review verdicts and final receipt in `~/.geppetto/maintain-memory.log`. The receipt records duration, known token usage, base and resulting revisions, and deferred and conflict counts. A verified run saves the per-bucket revisions and retains deferred candidates for the next run. An incomplete run keeps the prior cursor. Unresolved review conflicts appear through the existing throttled blocker notice. The log keeps verdicts and operation IDs and omits prompts, memory contents and model-written reasons.

Read `~/.geppetto/self-heal.jsonl` for each attempted repair, including the symptom, action, result and verification. `node skills/geppetto-adopt/scripts/heal.mjs` checks the current machine once. It can recreate missing launcher files from the registered package and prune Git registrations for absent managed worktrees. Memory maintenance registers its run under `~/.geppetto/worktrees` before creating an isolated profile or detached checkout. The `worktrees:memory-runs` repair removes those resources and their Git registrations after the registered owner exits. Abandoned lock recovery requires an exited owner and a ten-minute grace period. Repeated failures and recurring repairs appear as blockers. The health-store check rebuilds its recent corruption history from the repair journal. A healthy SessionStart reads the snapshot without adding context. A successful repair produces one notice across sessions.

Machine registrations for linked Git worktrees use the main checkout. Adoption still configures the checkout where it is invoked. Maintenance reads the main checkout’s project config, so commit and integrate shared settings there before relying on them in a scheduled run. Remove the durable registration from the main checkout. Legacy linked-checkout registrations can be removed by uninstalling in those checkouts.

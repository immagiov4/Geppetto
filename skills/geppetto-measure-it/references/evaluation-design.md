# Evaluation design

Choose the smallest check that can settle the claim:

- Typographical or wording changes without behavioural effect need no evaluation.
- A reproducible defect needs the failing test through `$geppetto-behaviour-tests`.
- A narrow procedure correction needs the reproducing case and a nearby case whose behaviour should stay unchanged.

Use the full sequence below for broad changes to agent behaviour, injected context, shared defaults or judged quality. Completion criteria describe sufficient evidence, not a form to fill in.

1. **Problem and metric.** State the observed problem with its evidence (signal keys, findings, traces), the metric it should move from [metrics](metrics.md) or project categories, and the metric at risk. Complete when a reader can tell which observation would show improvement.
2. **Hypothesis.** Write: in situations S, change X makes behaviour Y more (or less) frequent without worsening Z beyond an accepted limit. Name the result that would refute it, the smallest effect worth keeping and the keep/change/reject rule before seeing treatment results. Complete when the decision rule is fixed.
3. **Cases.** Draw cases from real episodes first, then user-supplied examples, then synthetic variations anchored on those. Include cases where the behaviour should occur and cases where it should not. Send each case through the real entry point with what a user would actually provide; do not name the expected behaviour, the expected source or the condition. When the question is whether an agent acts unprompted, keep an explicitly prompted arm separate from a realistic arm: the first bounds capability, only the second supports an adoption claim. Mark cases whose request or context already contains the answer. Isolate costly or irreversible side effects. For broad changes, freeze cases and hidden expectations before running the treatment, and keep pilot cases out of the decision set. Complete when each case states why it is representative and what it expects.
4. **Fair comparison.** Run baseline and treatment on the same cases, versions, model, reasoning level, tools and limits, in randomized or interleaved order, counting the same things the same way. For broad changes, disable the mechanism once and confirm the metric drops; otherwise the cases do not depend on it. For broad changes, repeat nondeterministic runs until run-to-run spread can be compared with the smallest effect worth keeping. Do not choose decision cases by their baseline score. Complete when a difference between arms can be attributed to the change.
5. **Checks and judging.** Use the cheapest check that observes the property: end state, test result or recorded action rather than the agent's account of its actions. Use a judge only for qualities a check cannot see; give it concrete criteria, hide the condition, prefer a pairwise comparison for before/after questions and avoid the subject's own model where possible. Before trusting a check, confirm a known-good output passes and an empty or plausible-but-wrong output fails. Read a few subject and grader traces for shortcuts: claimed actions that never happened, exposed answers, satisfied proxies. Complete when check errors cannot explain the result.
6. **Costs and regressions.** Report absolute time, tokens, cost and context size per arm beside the quality result and the metric at risk. Classify failed runs (timeout, harness or provider error, refusal, genuine failure) and keep infrastructure failures out of the score. Complete when quality, cost and failures are visible side by side.
7. **Decide.** Apply the rule from step 2. Retain cases or their identifiers, versions, results and limits at the owner. After adoption, learning audit reports on recurrence and unread changes show whether the effect holds in real use. Complete when the decision and its evidence are inspectable.
